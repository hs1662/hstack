# 옵트인 적대적 사전 검토 (`hstack-preflight`)

중요한 설계 변경이나 리팩터링에 착수하기 전에 사용자의 유도 전제를 제거하고, 읽기 전용 적대적 설계 검토관(`hstack-challenger`)의 코드 근거 반론과 내장 사용자 표결(`ask_question`)을 거쳐 합의된 방향만 실행한다.

## 지원 모드

1. **`/hstack-preflight [제안]` (기본 모드)**: 4단계 절차를 수행하고, 사용자의 명시적 표결이 확보된 경우에만 합의된 범위로 구현을 진행한다.
2. **`/hstack-preflight plan [제안]` (설계 전용 모드)**: 1~3단계만 수행하며 어떠한 경우에도 파일을 수정하거나 생성하지 않는다.
3. **`/hstack-preflight strict [제안]` (레드팀 모드)**: 2단계 위임 시 원안 기각을 기본 가설로 두고 반증 강도를 최대로 높여 검토하도록 지시한다.

## 4단계 절차

### 1단계: 실측 및 중립 브리프 작성 (탈고정)

- 관련 파일, 호출부, 테스트를 읽기 전용으로 직접 확인한다. 이 단계에서는 어떤 파일도 수정하지 않는다.
- 사용자의 유도 표현("깔끔하지 않을까", "전부 빼면 빠르지 않을까" 등)과 선호 어조를 모두 제거하고 아래 4항목으로만 중립 브리프를 정리한다.
  1. 해결하려는 문제
  2. 제안된 변경안
  3. 영향 예상 파일
  4. 명시된 제약

### 2단계: 격리 반론 위임

- `invoke_subagent` 도구로 `TypeName: "hstack-challenger"`, `Role: "적대적 설계 검토관"`을 호출하며 1단계에서 정리한 중립 브리프만 전달한다.
- `strict` 모드인 경우 "원안 기각을 기본 가설로 두고 모든 전제와 실패 모드를 최강도로 반증하라"는 반증 강도 지시만 덧붙인다.
- 반론 검토관의 최종 판정(`[사전검토 판정: 진행 가능]`, `[사전검토 판정: 조건부 진행]`, `[사전검토 판정: 재설계 권고]`)이 도착할 때까지 어떤 파일도 수정하지 않는다.

### 3단계: 대조 표 정리 및 내장 표결

- 원안, 반론 검토관의 핵심 반론(`파일:줄` 근거 포함), 최소 변경 기준선 및 대체 설계안을 하나의 비교 표로 요약한다.
- 내장 사용자 질문 도구 `ask_question`을 호출해 아래 4지선다 표결을 요청한다(`questions: [{ question, options, is_multi_select: false }]`):
  1. 원안대로 진행
  2. 조건부 보완안으로 진행
  3. 최소 변경/대체안 채택
  4. 구현 보류 및 추가 조사
- **비대화형 폴백 규칙 (필수)**:
  - `ask_question` 도구가 비활성화되어 있거나 오류를 반환하거나, 비대화형 실행 환경(`agy -p` 등)에서 응답 본문이 비어 있는 경우(예: `A1:` 뒤가 공백)에는 **절대 임의로 파일을 수정하지 않는다**.
  - 비교 표와 4가지 선택지만 사용자에게 한국어로 깔끔하게 출력하고 즉시 턴을 종료한다.

### 4단계: 합의안 실행 및 사후 감사 유지

- `plan` 모드가 아니고 사용자가 3단계 표결에서 ①~③ 중 하나를 명시적으로 선택한 경우에만 합의된 범위만 구현한다. 사용자가 ④를 선택하면 파일을 수정하지 않고 종료한다.
- 구현과 검증이 끝나면 기존 완료 검증 도구(`verify_completion`)와 고위험 변경 시 `TIER_1` 사후 독립 감사(`hstack-auditor`) 게이트를 정상 통과한다. 사전 검토는 사후 완료 검증이나 독립 감사를 절대 면제하지 않는다.

## 자율 발동 모드 (`[hstack:자동사전검토]`) — Silent-on-Green / Stop-on-Red

사용자가 슬래시 명령어를 입력하지 않았더라도, 안전장치 제거(`timingSafeEqual`, 파일 잠금, 만료·권한 검증, 하위 호환 폴백, `try/catch` 통삭제), 민감 경로 대규모 삭제, 또는 고위험 유도성 설계 변경 요청으로 프롬프트 라우터나 쓰기 서킷브레이커가 개입한 경우에는 아래 자율 분기 규칙을 따른다.

1. **중립 브리프 및 검토 요청**:
   - 관련 파일을 직접 읽어 중립 브리프를 정리한 뒤 `invoke_subagent`로 `TypeName: "hstack-challenger"`, `Role: "적대적 설계 검토관"`을 호출하며 프롬프트에 `[hstack:자동사전검토]` 표식을 포함한다.
2. **Silent-on-Green (`진행 가능` / `조건부 진행`)**:
   - 판정이 `[사전검토 판정: 진행 가능]`이면 지적된 잔여 리스크 1건 이상을 반영해 사용자 확인 팝업 없이 즉시 구현을 진행한다(단, 사용자가 코드 수정 없는 검토만 요청했다면 결과만 보고한다).
   - 판정이 `[사전검토 판정: 조건부 진행]`이면 사용자 목표와 충돌하지 않는 보완 조건을 자동으로 코드에 반영해 진행한다.
3. **Stop-on-Red (`재설계 권고`)**:
   - 판정이 `[사전검토 판정: 재설계 권고]`이면 즉시 코드 수정을 멈추고, `파일:줄` 근거와 대체 설계안을 요약한 비교 표와 함께 `ask_question`으로 사용자 표결을 받는다.
   - 비대화형 환경(`ask_question` 불가/빈 응답)이면 절대 파일을 수정하지 않고 비교 표와 선택지만 한국어로 보고한 뒤 종료한다.
4. **사후 감사 비면제**:
   - 자동 사전 검토에서 통과하더라도 `TIER_1` 민감·대규모 코드 변경에는 사후 `hstack-auditor` 독립 감사와 `verify_completion` 게이트가 동일하게 적용된다.
